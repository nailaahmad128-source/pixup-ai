# Platform scaffolding — what's real, what's a stub, what's missing

This project was extended beyond `lib/` + `android/` to include `web/`,
`linux/`, `windows/`, `ios/`, and `macos/` folders. They were hand-written
from the standard Flutter platform templates in an environment **without**
the Flutter SDK, Xcode, or network access — meaning none of this was
generated by (or verified against) the actual `flutter create` tool. Read
this file before assuming any platform "just builds."

## Status by platform

| Platform | Status | Notes |
|---|---|---|
| **android** | Real, previously audited | Builds against a real Gradle/Kotlin DSL setup — see the earlier audit. |
| **web** | Complete, standard template | `index.html`, `manifest.json`, generated icons. Low risk — plain text/JSON. |
| **linux** | Complete, standard template | CMake + GTK runner boilerplate. Low risk — plain text. |
| **windows** | Complete, standard template | CMake + Win32 runner boilerplate, generated `.ico`. Low risk — plain text. |
| **ios** | **Partial** | `Info.plist`, `AppDelegate.swift`, storyboards, `Assets.xcassets`, `Podfile`, generated icons — all present. **The actual Xcode project (`Runner.xcodeproj/project.pbxproj`) and workspace are NOT included.** |
| **macos** | **Partial** | Same pattern as iOS: plists, Swift files, xcconfigs, entitlements, icons present. **`Runner.xcodeproj/project.pbxproj` and `Runner.xcworkspace` are NOT included.** |

## Why iOS/macOS are partial, on purpose

`project.pbxproj` is a dense, internally cross-referenced file (build phases,
file references, and target settings linked by generated GUIDs). It's
normally written by Xcode/`flutter create`, not by hand. A hand-typed one
that's subtly wrong doesn't build with a clear error — it can fail to open
in Xcode at all, or open and silently drop build phases. Shipping a fake
one under the label "complete project" would be worse than leaving it out.

**The fix is one command, run on a machine with Flutter installed:**

```bash
cd pixup_ai
flutter create --platforms=ios,macos .
```

This only adds the missing `.xcodeproj`/`.xcworkspace` files — it will not
touch your existing `lib/`, `pubspec.yaml`, or `android/`. It's the same
command referenced in the main README for regenerating `android/gradlew`,
`local.properties`, etc., just scoped to the two remaining platforms.

## A more fundamental limit: several dependencies are mobile-only

Even with perfect scaffolding, **this specific app will not build for
web/linux/macos/windows as-is**, because key packages in `pubspec.yaml`
don't ship implementations for those platforms:

- `onnxruntime` — Android/iOS only. No web/desktop ONNX inference backend.
- `ffmpeg_kit_flutter_new` — Android/iOS only.
- `gal` (save to gallery) — Android/iOS only; no equivalent "gallery" concept
  on desktop/web.

`image_picker`, `share_plus`, `url_launcher`, and `video_player` do have
desktop/web plugin implementations, so the UI shell would run — but the
core AI photo/video enhancement feature (the entire point of the app)
would not, since neither the ONNX inference path nor the FFmpeg pipeline
exists on those platforms. The `flutter/generated_plugins.cmake` files
under `linux/` and `windows/` in this package list only the plugins that
plausibly have desktop implementations, as a placeholder — `flutter pub
get` will overwrite them with the real, correct list once you run it.

**If you actually want this app on web/desktop**, that's a real feature-design
task, not a scaffolding one: you'd need a conditional/alternate
`AIEnhancementService` implementation per platform (e.g. a cloud API call
instead of on-device ONNX for web, or accepting that desktop only gets the
FFmpeg-less filter path), then swap it in via the same interface already
described in the main README's "Connecting a different/cloud AI engine
later" section.

## What to do next, in order

1. `flutter pub get` (regenerates the two `generated_plugin_registrant`
   stub files correctly for whichever platforms your resolved packages
   actually support).
2. `flutter create --platforms=ios,macos .` to get real Xcode projects.
3. `flutter doctor` and fix anything it flags per-platform (Xcode CLT,
   CocoaPods, Visual Studio Desktop workload, GTK dev libraries, etc.).
4. Then build per-platform: `flutter build apk`, `flutter build ios`,
   `flutter build macos`, `flutter build windows`, `flutter build linux`,
   `flutter build web`.
5. Re-read the main `README.md` for the still-outstanding items from the
   Android audit (ONNX model binary, release keystore, GPL licensing
   review for `ffmpeg_kit_flutter_new`) — those apply regardless of platform.
